# 留白原型版本管理

以项目根目录为命令工作目录。先读 [原型索引](../../../prototype/README.md) 确认当前版本和状态，再读 [原型规则](../../../prototype/AGENTS.md) 与 [工作流程](../../../prototype/工作流程.md)。详细步骤以工作流程为单一来源，不另复制规则。

## 按用户请求选择操作

- **开始下一版**：从索引指定的最新定稿创建下一版本，起初仅创建未定稿 HTML；存储键独立，文件头记录基线与待确认项。不要因为用户要求修改已经存在的草稿，就反复创建新版本。
- **修改未定稿**：继续当前草稿，必须执行[修改未定稿与方案对比](../../../prototype/工作流程.md#修改未定稿与方案对比)，据此处理产品前后对比、辅助区修改例外、编号标题与 Tab 结构，以及预览、方案确认和定稿的边界。
- **定稿**：以用户明确确认的方案为依据；尚有影响产品行为的未决问题时先询问。归档比较稿，输出只包含已采用实现的定稿及方案存档、版本迭代文档（总计三份）。清理隐藏的未采用代码，不能仅隐藏切换入口；保留真实产品状态与交互。
- **文档修订**：不改变产品行为时可修正本版文档并记录修订；不再创建或更新命名表与命名图。
- **开发交接**：读对应定稿和最终差异，关联区域名称与验收条件。原型定稿不代表原生开发或验收已完成；只按用户请求的开发范围继续。

## 资料与校验

使用项目现有脚本检查定稿：

```sh
node scripts/check_prototype.cjs vX.Y
```

替换版本参数后运行。脚本要求该版本已有定稿，未定稿阶段不为满足脚本而补造定稿。检查覆盖菜单栏、任务规则及部分版本专项行为；后续规则改变需同步调整检查，不能仅凭旧测试通过就宣布新功能验收完成。

检查真实版本差异、方案编号稳定性、存储隔离和相对链接。历史命名资料冻结保留；当前及后续版本用区域名称、定稿和版本迭代定位需求。能够实际操作页面时检查本次变化；不能操作时说明源码检查覆盖范围与未验证项。最终报告链接到版本索引和本次产物，分别说明原型、实现和验收状态。

历史版本无法证实已定稿时，保留实际资料并注明未知。遇到用户最新确认与定稿或文档冲突，明确冲突点并暂停该部分，不从历史方案稿自行推断新的产品决策。
