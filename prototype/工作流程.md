# 原型版本工作流程

## HTML 预览

1. 确认目标 HTML 的真实路径。原型版本与状态以 `prototype/README.md` 为准；直接服务项目中的原文件，保留相对资源路径。
2. 优先复用已确认服务目录正确、可访问的本地 HTTP 服务。没有合适服务时，以包含所需资源的最小目录为服务根目录，仅绑定 `127.0.0.1`。例如从项目根目录运行：

   ```sh
   python3 -m http.server 8770 --bind 127.0.0.1 --directory prototype
   ```

   端口为示例；遇到端口占用时选择空闲端口，不终止未知进程。预览期间保持服务运行。
3. 服务成功启动后，按相对路径构造 URL；中文和空格等字符按 URL 路径段编码。确认目标 URL 返回目标 HTML，再打开浏览器。
4. 使用 `open_in_codex`，传入 `target.type = "browser"` 和目标 HTTP URL，在当前任务中打开预览。打开源文件面板不能代替网页预览。
5. 按工具实际结果报告：返回 `queued` 时说明“已请求打开”；只有得到页面已显示的证据后才说明“已打开”。最终提供预览链接和源文件链接。
6. 启动服务遇到沙箱权限限制时，按工具规定申请执行权限；浏览器访问明确被拒绝时，不通过更换地址或工具绕过。工具不可用时说明限制并提供可用的访问地址。
7. 打开和预览不代表方案确认、定稿或验收通过。

## 开始新版本

1. 读根版本索引、最新定稿、对应迭代文档；明确产品版本与原生实现状态。
2. 从最新定稿创建下一版本目录，只新建 `留白-vX.Y-未定稿.html`。
3. 更换为该版本独立存储键；添加与产品水平并排且内容内部滚动的交互方案区域。
4. 文件头注释记录基线版本、修改项、已确认事项、待确认事项。发生产品修改时，按下节创建对比选项；仅建立基线副本时不虚构修改方案。

## 修改未定稿与方案对比

### 适用范围与确认边界

- 修改产品原型的界面、样式、布局或交互行为时，必须在左侧「留白 · 交互方案」区域提供修改前、修改后的可切换方案，供用户实际体验和评判。选项必须切换对应界面及交互，不能只有文字说明。
- 「留白 · 交互方案」是辅助评审区域。其自身的布局、样式和文案直接修改，无需为辅助区域再创建对比选项。定稿时从定稿文件中移除整个辅助区域及相关比较代码，方案存档保留对比内容。
- 已确认要求不重新作为未决问题提出；未定稿阶段仍保留修改前方案供对照。点击 Tab 仅表示预览，不代表确认或定稿。用户可通过「第 1 项选 B」或「确认 1B」指明方案；最终生成定稿仍须用户明确要求。

### 方案区结构与操作规范

1. 保留总标题「留白 · 交互方案」。区域与产品水平并排，内容超高时在区域内部滚动。
2. 每个配置组只包含两部分：带序号的标题和 Tab 选项区。不添加介绍、操作说明、决策记录等额外内容；必要资料写入文件注释或版本文档。
3. 标题采用「序号. 修改对象」格式，使用中性描述，例如「1. 倒计时展示与任务切换」，不加入优劣评价。
4. 选项采用「大写字母 + 简短方案名」格式，例如「A 状态栏」「B 悬浮块」，不使用“修改前”“修改后”“优化后”等前缀。通常 A 对应修改前，B 起对应修改方案。
5. Tab 横向排列，空间不足时自动换行；组内单选，选中态通过底色和边框明显区分。
6. 不同修改项分别成组；存在依赖、不能独立组合的变化合为一个方案组，避免产生无效组合。
7. 配置组序号和选项字母一经分配保持稳定，新增项依次追加，删除后不复用，不因调整显示顺序而重新编号。

## 用户确认定稿

只有用户明确确认才定稿，不以“看起来完成”代替确认。

1. 未定稿重命名为同版本“方案存档”，记录最终选择，之后只供回顾。
2. 生成定稿 HTML，移除比较面板、未采用 HTML/CSS/JS、旧入口及方案存储；保留实际产品所有状态分支。用清楚的函数名和格式，不压缩成难读代码。
3. 创建版本迭代文档：真实基线、最终新增／修改／移除、关键决策、区域名称、交互边界、验收条件、数据兼容、模拟限制。
4. 运行 `node scripts/check_prototype.cjs vX.Y`（后续功能扩展需同步增加对应检查），检查脚本语法、关键变化、文档链接和定稿清理结果；记录未验证项。浏览器访问被拒绝时不得另换地址或工具绕过。
5. 更新根索引：定稿状态、实现状态、验收记录入口分别填写。不得自动宣称已开发或已验收。

## 冻结与修订

功能或交互改变进入下一版本。原版本可修正错别字、坏链接、遗漏的既有规则，记入版本迭代文档的修订部分。纯代码清理需保留旧文件并验证行为不变；未经视觉复核明确标注，不自动视为重新验收通过。

遇到最新确认、定稿与文档互相冲突，暂停询问用户，不凭历史草稿覆盖已确认规则。历史无可靠定稿不补造资料。

## 开发交接

输入：用户最新明确确认 + 定稿 HTML + 版本迭代文档。对话提供背景，关键需求应落入版本文档。实际测试结果留在项目验收记录，原型索引链接过去，不重复维护状态。

Rule 承载本流程的约束；项目 Skill `.agents/skills/still-prototype-versioning/SKILL.md` 按请求选择操作并引用本流程；脚本负责机械生成与校验。详细步骤只维护在本文。
